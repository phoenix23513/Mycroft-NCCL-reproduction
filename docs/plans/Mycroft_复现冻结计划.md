# Mycroft 复现冻结计划

- 版本：v1.0
- 冻结日期：2026-08-11
- NCCL 目标版本：2.21.5
- 短期目标：完成一个可以运行、可以注入异常、可以输出定位结果的 Mycroft 最小复现
- 最终目标：把最小复现中的观测逻辑接入 NCCL 2.21.5，并在具备条件的多 GPU／多机环境中验证

## 1. 这份计划解决什么问题

此前的学习把“讲过一个概念”“看过一段代码”和“已经掌握、能够用于复现”混在了一起，也缺少稳定的实验主线。本计划从 Mycroft 的输入、处理过程和输出反推必须学习的 NCCL 内容，并用实验产物验收。

从现在开始，学习状态只使用以下四种：

| 状态 | 含义 |
|---|---|
| 未开始 | 尚未系统学习，也没有实验产物 |
| 已讲授 | 已经解释过，但没有通过实际产物证明掌握 |
| 已验证 | 已产生规定的实验结果，并通过本阶段验收 |
| 环境阻塞 | 已完成可做部分，但缺少编译、GPU、网络或多机条件 |

**“已讲授”不再等于“阶段完成”。**

## 2. 先确定复现边界

Mycroft 论文描述的完整实现并不是“不到 1000 行”：论文给出的规模约为 **1100 行 NCCL C++ 插桩代码，加约 4000 行 Python 后端代码**。因此必须区分三种复现范围。

### 2.1 L1：本机最小复现（当前主目标）

输入是模拟或离线生成的多 rank 运行轨迹；系统能够：

1. 记录 collective、rank、channel、操作序号和三类进度量；
2. 模拟 GPU、Proxy 和网络的先后依赖；
3. 注入 GPU 未准备、Proxy 未发送、网络未完成等异常；
4. 检测停滞或慢速 collective；
5. 区分根因 rank 和被阻塞 rank，并输出证据链。

这一层不要求真正编译 NCCL，也不依赖 RDMA 或多 GPU。它验证的是 Mycroft 的核心推理是否被正确复现。

### 2.2 L2：NCCL 2.21.5 插桩原型

把 L1 已验证的事件模型接入 NCCL 2.21.5：

- 在准确的源码位置采集 `GPU_ready`、`RDMA_transmitted`、`RDMA_done`；
- 建立跨 rank 可关联的操作身份；
- 写入 Host 共享内存循环缓冲区；
- 由独立读取程序导出轨迹；
- 使用 `nccl-tests` 或最小测试程序验证。

这一层需要可用的 CUDA/NCCL 编译环境；真实验证最好需要至少两张 GPU。

### 2.3 L3：论文规模复现

论文环境包括多机、多 GPU、RDMA 网卡以及实际 LLM 训练负载。当前单 GPU WSL 环境无法验证这一层。它属于后续有集群资源时的扩展目标，不作为 L1 完成条件。

## 3. Mycroft 反推出来的必学内容

### 3.1 必须掌握

| 必须掌握的内容 | 为什么 Mycroft 需要它 |
|---|---|
| NCCL API、Host、GPU kernel、Proxy/NET 三条执行线 | 判断某个进度量由谁更新，异常停在哪一层 |
| communicator、rank、collective 操作序号 | 区分并关联不同通信组和不同操作 |
| task、device work、kernel plan 的转换关系 | 从一次 API 调用追到 GPU 实际执行的工作 |
| Ring AllReduce 的 chunk 依赖 | 解释为什么一个 rank 的故障会阻塞其他 rank |
| send/recv Proxy 操作的生命周期 | 找到 ready、transmitted、done 的真实更新位置 |
| channel、连接、QP 的身份关系 | 将一次 collective 拆成可以观测的通信流 |
| 循环缓冲区和独立读取进程 | 低干扰地从 NCCL 导出运行状态 |
| 触发器、MinOp、MinData 和状态判定 | 从轨迹得到根因定位结果 |

### 3.2 当前暂缓

以下内容不是永远不学，而是不允许它们打断当前复现主线：

- Tree、CollNet、NVLS 的完整算法实现；
- LL、LL128 的全部模板细节；
- 完整的 channel 负载均衡策略；
- CUDA 模板和宏展开的所有实现技巧；
- RDMA verbs 的系统课程；
- Kafka、云端存储和生产级 Web 服务；
- 论文全部大规模训练实验的复刻。

此前已经使用九阶段结构。为了避免再次换计划，本计划保留阶段 0—8，只重新明确每个阶段为 Mycroft 解决什么问题、用什么产物验收。

| 阶段 | 核心问题 | 当前状态 | 验收产物 |
|---|---|---|---|
| 0. NCCL 使用边界 | 谁在什么情况下调用 NCCL，调用返回代表什么 | 已讲授 | 一次调用的 Host/GPU/Proxy 时间线 |
| 1. Communicator 初始化 | 哪些 GPU/rank 属于同一通信域，身份如何建立 | 已讲授 | 2 rank 初始化对象关系图 |
| 2. Host 任务提交 | `ncclAllReduce()` 如何形成 `ncclTaskColl` | 已讲授 | 从 API 到 task 的字段追踪表 |
| 3. Device 工作与 launch | task 如何形成 `ncclDevWorkColl` 并被 plan 组织 | 已讲授 | task/work/plan 生命周期图 |
| 4. Ring 数据依赖 | chunk 如何经过 ReduceScatter 和 AllGather | 已讲授 | 可运行的 4-rank Ring 模拟器 |
| 5. Proxy 与传输进度 | GPU、Proxy、网络分别推进什么状态 | 已讲授一部分 | 三进度量状态机模拟器及 send/recv 源码图 |
| 6. 可观测事件与身份 | 怎样跨 rank 关联一次操作和一条流 | 未开始 | 事件模式和 NCCL 2.21.5 字段来源表 |

| 8. 插桩、集成与评估 | 怎样接入 NCCL 并验证故障定位 | 未开始 | L1 完整系统；环境允许时完成 L2 原型 |

阶段 0—4 不能直接标记为完成。它们将通过阶段 4 的综合实验一次性验收；失败的部分只补对应缺口，不从头重讲。

## 5. 实际执行顺序

### 阶段 4 验收：实验 E01——4-rank Ring 依赖模拟器

**目的**

把此前学过但没有验证的阶段 0—4 串成一个可以运行的整体，并第一次直接服务于 Mycroft 的“依赖传播”问题。

**先补充的知识**

- 只复习本实验需要的 Ring 顺序、chunk、step、send/recv；
- 每出现一个新名称，都注明它是结构体、结构体指针、函数、成员还是队列；
- 使用 C 风格描述指针和数据结构。

**实验内容**

- 固定 4 个 rank，先实现单 channel、固定 Ring 顺序；
- 对一个小数组执行 ReduceScatter + AllGather；
- 每一步输出 JSONL 事件：`op_seq/rank/channel/step/chunk/action/peer/timestamp`；
- 给一个 rank 注入延迟，展示延迟如何传播到后继 rank；
- 数值结果仍要与直接求和一致。

**验收标准**

1. 正常运行时四个 rank 得到相同的 AllReduce 结果；
2. 事件顺序能解释每个 chunk 的上游和下游；
3. 注入延迟后，能够区分“最早发生异常的 rank”和“后来被阻塞的 rank”；
4. 用户能够借助输出回答一个实际问题：为什么观察到的最慢 rank 不一定是根因 rank。

**预算：6—8 个专注小时。**

### 阶段 5：实验 E02——GPU/Proxy/网络三段状态机

**目的**

把论文中的三个进度量变成真实的执行顺序，而不是三个孤立名词。

**学习内容**

- send 侧和 recv 侧分别是谁生产数据、谁发起网络操作、谁确认完成；
- `GPU_ready`、`RDMA_transmitted`、`RDMA_done` 的大小关系；
- NCCL Proxy 是 Host 进程内由 NCCL 创建的 CPU 线程，不是另一台机器，也不是 GPU 线程；
- 只学习理解 QP、请求提交和完成检查所需的最小网络知识。

**实验内容**

- 用三个逻辑执行者模拟 GPU producer、Proxy、Network completion；
- 分别注入 GPU 延迟、Proxy 延迟和网络完成延迟；
- 周期性输出三个累计进度量；
- 生成论文四类状态：未开始、未发送、未送达、GPU 未继续准备。

**验收标准**

给定一段状态轨迹，不依赖名词解释，而是能指出：哪个执行者没有推进、阻塞会传给谁、还缺什么证据才能断言根因。

**预算：6—8 个专注小时。**

### 阶段 6：实验 E03——事件身份和源码映射

**目的**

解决“多个 rank、多个 communicator、多个 channel 的事件怎样属于同一次操作”这一问题。

**学习和源码范围**

- 只针对 NCCL 2.21.5，不再用当前 master 的字段替代结论；
- 建立 `IP/comm_id/Gid/GPU_id/channel_id/QP_id/op_seq/msg_size` 的来源表；
- 对每个字段记录：创建者、保存结构、生命周期、是否跨 rank 一致、是否足以唯一标识；
- 确认三个进度量在 send/recv 路径中的候选插桩位置。

**实验内容**

让 E01、E02 使用同一事件格式，混合两组 communicator 和多个操作，再由解析程序恢复每组操作的时间线。

**验收标准**

1. 不靠事件到达顺序也能正确分组；
2. 每个身份字段都有 NCCL 2.21.5 源码依据；
3. 尚未确认的字段明确写成“待确认”，不把猜测写成成果。

**预算：8—12 个专注小时。**

### 阶段 7：实验 E04——Mycroft 分析器 MVP

**目的**

完成第一个真正可演示的 Mycroft 最小复现。

**功能**

- 读取 E01—E03 生成的多 rank JSONL；
- 完成停滞触发和慢速触发；
- 计算最小已完成操作 `MinOp`；
- 在同一操作中比较最小传输进度 `MinData`；
- 使用三进度量状态和依赖关系输出根因候选；
- 输出“根因候选、受影响 rank、证据、置信边界”，不只输出一个标签。

**故障用例**

至少覆盖：GPU producer 延迟、Proxy 发送延迟、网络完成延迟、某 rank 整体停止、正常但负载不均。

**验收标准**

- 每类故障都有固定输入和期望输出的自动测试；
- 不把下游受害 rank 错报为唯一根因；
- 正常慢波动不会被简单地当作故障；
- 能用一张时间线解释分析器为何给出该结论。

**预算：8—12 个专注小时。**

完成本阶段即达到 **L1 本机最小复现**。

### 阶段 8A：实验 E05——共享内存循环缓冲区与读取程序

**目的**

复现论文的低干扰数据采集结构，为接入 NCCL 做准备。

**内容**

- 固定大小事件结构；
- Host 共享内存循环缓冲区；
- 写入方不等待分析方；
- 独立只读程序批量导出；
- 明确覆盖、丢事件和版本兼容策略。

**验收标准**

高频写入时业务线程不因读取程序变慢而阻塞；输出能被 E04 分析器直接读取；溢出行为可观察。

**预算：6—10 个专注小时。**

### 阶段 8B：实验 E06——接入 NCCL 2.21.5

**前提**

- 获取并固定 NCCL 2.21.5 源码；
- CUDA Toolkit、编译器和测试程序可用；
- 单 GPU 环境只能完成编译和有限路径验证；真实通信验证需要多 GPU；RDMA 路径需要多机和相应网卡。

**内容**

- 插桩点控制在论文所述的小数量关键位置；
- 事件写入 E05 的缓冲区；
- 运行最小 AllReduce workload；
- 用 E04 分析器读取真实事件；
- 先注入软件延迟，再考虑网卡限速、PCIe 降级等硬件实验。

**验收标准**

1. NCCL 2.21.5 能稳定编译；
2. 正常 AllReduce 结果不受插桩影响；
3. 真实事件能够形成完整操作时间线；
4. 软件延迟用例能被检测并定位；
5. 记录插桩开销和丢事件情况。

**预算：12—20 个专注小时，不包含环境修复和获取多 GPU 资源的等待时间。**

完成本阶段即达到 **L2 NCCL 插桩原型**。

### 阶段 8C：多机和论文实验扩展

在获得集群后再执行：RDMA 路径验证、真实 QP 身份、网卡故障和限速、GPU 限功率、背景计算/流量、LLM 训练负载。预算取决于集群权限和故障注入方式，不能计入当前本机承诺。

## 8. 讲解、自测和计划变更规则

### 8.1 讲解规则

1. 先给本节在完整流程中的位置和实际问题，再引入细节；
2. 每个新名称首次出现时说明类型：结构体、结构体指针、函数、成员、队列或线程；
3. 概念与调用顺序、数据变化和源码位置同时出现；
4. 优先使用 C 风格表述；
5. 示例必须标清简化条件，不能把单 channel 示例说成 NCCL 的唯一实现。

### 8.2 自测规则

- 自测只考本阶段实际讲过或实验实际产生的内容；
- 以追踪流程、读事件、判断阻塞和解释代码为主；
- 不出依赖未知 UniqueId、虚构情景或纯名词辨析的题；
- 每道题同时标注考查目标和答案依据；
- 自测不是阶段完成证据，实验验收才是。

### 8.3 变更规则

九个顶层阶段冻结。若必须调整，只能提交一条明确的变更记录，包含：

1. 哪个验收结果证明原路线受阻；
2. 具体调整哪一项，不允许笼统地“重做计划”；
3. 对时间和目标有什么影响；
4. 哪些内容被延期而不是悄悄删除；
5. 得到用户确认后再执行。

任何新实验在执行前都必须先说明：它解决什么问题、产出什么、预计成本是多少。不得因为想到一个工具或例子就改变主线。
